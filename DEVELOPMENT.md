# Разработка и запуск Fragrance

## Требования

Node.js 22+, npm и MySQL 8. Проверки выполнены на MySQL 8.0.46. Клиент и API обслуживаются одним Express-сервером, по умолчанию только на локальном интерфейсе.

## Первый запуск

1. Открыть папку проекта в VS Code и выполнить `npm ci`.
2. Создать `.env` по `.env.example`. Задать `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `PORT` и `SESSION_SECRET`. Секрет сессии — случайная строка минимум из 32 символов. Получить её можно командой `node -e "console.log(require('node:crypto').randomBytes(48).toString('hex'))"`. Не публиковать результат и `.env`.
3. Только для новой базы импортировать `db/perfume_database.sql` через MySQL Workbench. Начальное имя — `scent_craft_db`; указать его в `.env`. Не импортировать наполнение повторно в существующую базу.
4. Выполнить `npm run migrate`. Это доводит исходную схему до 15 таблиц и сохраняет каталог и старые заказы.
5. Выполнить `npm run dev` (автоматический перезапуск) или `npm start`. Открыть `http://localhost:3000/beginners.html`, заменив порт на заданный в `.env`. Остановка — Ctrl+C.

Если PowerShell блокирует `npm.ps1`, можно использовать `npm.cmd`. Если возникает `ER_ACCESS_DENIED_ERROR`, проверить вход в Workbench с теми же адресом, портом и пользователем и исправить локальный пароль. Изменение SESSION_SECRET не исправляет авторизацию MySQL. Переменные, уже заданные в терминале, имеют приоритет над `.env`.

Для миграций нужны права изменения схемы. Приложению нужны чтение и запись в прикладные таблицы и сессии. В режиме `production` cookie требует HTTPS; настройка прокси и публикация не входят в локальный запуск.

## Администратор

Зарегистрировать аккаунт через приложение и выполнить `npm run admin:grant -- <email-аккаунта>`. После обновления личного кабинета появится ссылка на `/admin.html`. Команда использует ту же базу из окружения. Публичного API назначения роли нет.

## База и обновление

Подробности связей — в `db/README.md`. Файл `db/schema.sql` содержит актуальный снимок структуры без пользовательских данных и служит для изучения схемы. Он не заменяет первоначальное наполнение и миграции.

Существующую установку обновлять через `npm run migrate`. Не пересоздавать базу. Перед применением к рабочим данным сделать резервную копию. Миграции 001–003 добавляют конструктор, аккаунты, заказы и доступность каталога; 004 добавляет справочники и журнал статусов. Строковые идентификаторы и JSON базовых нот сохраняются.

Каждая SQL-команда миграции учитывается в `schema_migrations`. Повторный успешный запуск пропускает выполненное. MySQL DDL не является общей транзакцией: при прерывании между SQL и записью отметки нужно проверить фактическую схему перед повтором. Обработчик рассчитан на простые SQL-команды, без процедур и разделителей внутри строк.

## API

Все тела изменяющих запросов — JSON. Для сессионных маршрутов сначала получить `GET /api/auth/me` и передавать возвращённый токен в `X-CSRF-Token`. После входа токен меняется.

| Маршруты | Назначение |
| --- | --- |
| GET /api/atmospheres, GET /api/bottles | Публичный активный каталог |
| POST /api/quote | Цена по atmosphereId, accentId, bottleId; возвращает totalMinor и BYN |
| GET /api/auth/me | Пользователь или null и CSRF-токен |
| POST /api/auth/register, /api/auth/login, /api/auth/logout | Регистрация, вход, выход |
| PATCH /api/profile | Имя и телефон текущего пользователя |
| GET, POST /api/cart; PATCH, DELETE /api/cart/:id | Корзина владельца |
| POST /api/orders | Заказ по revision корзины и UUID checkoutKey |
| GET /api/orders, /api/orders/:id | Последние 100 своих заказов и подробности |
| POST /api/orders/:id/cancel | Отмена своего нового заказа |
| POST /api/orders/:id/repeat | Все композиции своего заказа в корзину по текущим ценам |
| GET /api/admin/images | Допустимые изображения из images |
| GET, POST /api/admin/catalog/:kind | Список и создание atmospheres, accents, bottles |
| PUT, DELETE /api/admin/catalog/:kind/:id | Редактирование и удаление |
| PATCH /api/admin/catalog/:kind/:id/visibility | Булево active |
| GET, PUT /api/admin/atmospheres/:id/accents | Совместимость, запись массива accentIds |
| GET /api/admin/orders, /api/admin/orders/:id | Заказы администратора |
| PATCH /api/admin/orders/:id/status | status и expectedStatus |

Панель требует роль admin. Списки администратора содержат по 25 записей, страница задаётся `page`. Каталог: `q`, `state=all/active/hidden`, `sort=name/price`, `direction=asc/desc`. Заказы: `number`, `status`, `from`, `to`. Даты — YYYY-MM-DD, последний день включается целиком по времени MySQL.

Подробности заказа содержат `items` со снимками покупки и `history` с `from_status`, `to_status`, `event_kind`, `changed_at`. Личные данные автора в публичную часть истории не выдаются. На уровне БД автор хранится в `actor_id`. Поле `event_kind=migration` означает фиксацию состояния при переходе на новую схему, а не фактическое время прежней смены статуса.

Конфликт revision или expectedStatus возвращает 409; недоступный состав — 422. Заказ с очисткой корзины и смена статуса с записью журнала атомарны. Скрытые товары нельзя заказать; удаление связанных с заказами или корзинами компонентов блокируется внешними ключами. Новая категория автоматически добавляется при сохранении ноты в той же транзакции.

## Проверки

`npm test` запускает тесты. Без TEST_DB_NAME интеграционная MySQL-проверка явно пропускается. Для полной проверки использовать отдельный MySQL и новое имя базы:

```powershell
$env:DB_HOST = '127.0.0.1'
$env:DB_PORT = '3307'
$env:DB_USER = 'test_user'
$env:TEST_DB_NAME = 'fragrance_test_run1'
npm test
```

Пароль передать через локальную DB_PASSWORD. Тестовый пользователь должен иметь право создать базу. Тест отказывается использовать существующую БД или имя без fragrance_test_. Созданная БД сохраняется для осмотра, следующий запуск требует другого имени.

На этапе расширения хранилища прошли все 17 проверок: миграции, сохранность каталога, цена, вход и CSRF, права, корзина, оформление и повторы, откат при сбое, администрирование, совместимость, статусы, 15 таблиц и внешние ключи, атомарность журнала. Отдельно проверено обновление прежней тестовой БД с пользователями и заказом: данные до и после совпали, история переноса не продублировалась.

Ранее в браузере проверены конструктор, путь покупателя до заказа и отмены, формы каталога администратора, ошибки и узкий экран. В текущем этапе менялись сервер и хранилище; новых визуальных проверок нет. История событий теперь отображается в подробностях заказа у покупателя и администратора.

Основная пользовательская MySQL ранее отклоняла авторизацию. Новая миграция проверена на отдельном тестовом сервере и не применялась к основной базе.

## Повтор заказа и история в интерфейсе

Повтор переносит все позиции собственного заказа в существующую корзину, сохраняя названия и количества. Проверяются текущие цены, доступность, совместимость и лимит в 20 композиций. При ошибке вся операция откатывается. Сам новый заказ не оформляется: покупатель отдельно проверяет сумму и подтверждает корзину. Повторный самостоятельный вызов маршрута снова добавляет позиции; кнопка блокируется после успешного добавления в текущем открытом заказе.

На этом этапе прошли 20 автоматических проверок, включая доступ к чужому заказу, CSRF, актуальные цены, лимит корзины и откат частично перенесённых позиций. В браузере проверены успешный повтор, недоступный компонент, история создания и отмены, отображение в панели администратора и узкий экран 390 × 844.
