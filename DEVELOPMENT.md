# Локальная разработка Fragrance

## Запуск

Нужны Node.js 22 или новее, npm и MySQL 8. Проверки первого этапа выполнены на MySQL 8.0.46. Интерфейс и API обслуживаются одним Express-сервером.

1. Выполнить `npm ci`.
2. Создать локальный `.env` по `.env.example`, указать свои настройки MySQL и случайный `SESSION_SECRET` длиной не менее 32 символов. Значения паролей со специальными символами заключать в двойные кавычки. `.env` исключён из Git. Секрет сессии должен оставаться одним и тем же между перезапусками сервера; при его замене пользователи входят заново.
3. Если база ещё не создана, однократно импортировать `db/perfume_database.sql` через MySQL Workbench. Для существующей базы повторный импорт не нужен: начальное наполнение не рассчитано на повторный запуск.
4. Выполнить `npm run migrate`, чтобы добавить цены, флаконы, пользователей, сессии, корзины, заказы и признаки доступности каталога. Существующие атмосферы, ноты и их связи сохраняются.
5. Выполнить `npm start` и открыть http://localhost:3000/beginners.html. Для разработки с перезапуском сервера при изменениях — `npm run dev`.

`DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` задают подключение к MySQL. `PORT` задаёт порт приложения. Старое имя базы `scent_craft_db` сохранено для совместимости с существующими данными; бренд приложения — Fragrance. Сервер по умолчанию слушает только локальный интерфейс.

При ошибке доступа MySQL проверить учётную запись и её доступ к выбранной базе. Приложение не сбрасывает пароли и не пересоздаёт пользовательскую базу. Для миграций нужны права создания и изменения таблиц; для обычной работы приложения нужны чтение и запись в таблицы пользователей, сессий, корзин и заказов.

`NODE_ENV=development` используется для локального HTTP. В режиме `production` сессионная cookie требует HTTPS. Конфигурация обратного прокси и HTTPS в текущий локальный этап не входит.

## Миграции

Последовательные SQL-миграции находятся в `db/migrations`; выполненные шаги учитываются в `schema_migrations`. Повторный успешный запуск пропускает применённые шаги. Миграции запускаются отдельно от приложения, а не при каждом старте сервера.

MySQL выполняет DDL с неявным commit. Если процесс прервался между выполнением SQL и записью отметки, нужно проверить фактическую схему и отметку шага перед повтором. Не удалять пользовательские данные для исправления миграции. Используемый обработчик рассчитан на простые SQL-команды без хранимых процедур и разделителей внутри строк.

## Проверки

`npm test` запускает проверки расчёта стоимости, валидации запросов и недоступности серверных файлов по HTTP. Проверка MySQL пропускается без `TEST_DB_NAME`, что явно отображается в результате.

Для интеграционного теста задать через окружение параметры отдельного тестового MySQL и новое имя базы с префиксом `fragrance_test_`, затем запустить `npm test`. Например, в PowerShell:

```powershell
$env:DB_HOST = '127.0.0.1'
$env:DB_PORT = '3307'
$env:DB_USER = 'test_user'
$env:TEST_DB_NAME = 'fragrance_test_constructor_run1'
npm test
```

Пароль тестового пользователя передавать локально через `DB_PASSWORD`; не сохранять его в истории общих инструкций. Учётная запись теста должна иметь право создать базу. Тест отказывается использовать существующую базу или имя без указанного префикса. После проверки база сохраняется для осмотра; следующий запуск требует нового имени.

Интеграционная проверка создаёт исходный каталог, дважды применяет миграции, проверяет сохранность данных, шесть флаконов, расчёт цены, недопустимое сочетание и отключённый флакон, а также HTTP-ответы API.

## API первого этапа

- `GET /api/atmospheres` — массив атмосфер со связанными акцентами; исходный контракт сохранён, добавлены цены за мл.
- `GET /api/bottles` — доступные варианты флаконов.
- `POST /api/quote` — расчёт по `atmosphereId`, `accentId`, числовому `bottleId`. Возвращает выбранные компоненты, `totalMinor` в копейках и `currency: BYN`. Переданная клиентом цена не используется.

Формула: `(основа за мл + акцент за мл) × объём + флакон`. Расчёт выполняется в целых копейках. Черновик хранится в браузере, корзина и оформленные заказы — в MySQL.

## API покупателя

- `GET /api/auth/me` — текущий пользователь и CSRF-токен; сначала вызывается и гостем.
- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout` — регистрация, вход и выход.
- `PATCH /api/profile` — изменение имени и телефона своего аккаунта.
- `GET /api/cart`, `POST /api/cart`, `PATCH /api/cart/:id`, `DELETE /api/cart/:id` — корзина пользователя.
- `POST /api/orders` — оформление по актуальной `revision` корзины и UUID `checkoutKey` для защиты от повторной отправки.
- `GET /api/orders`, `GET /api/orders/:id` — последние 100 заказов пользователя и детали одного заказа.
- `POST /api/orders/:id/cancel` — отмена своего нового заказа.

Изменяющие запросы передают объект JSON и заголовок `X-CSRF-Token`. После входа токен обновляется. Пароли хешируются bcrypt; сессии хранятся в MySQL, срок действия cookie — сутки. Cookie использует HttpOnly и SameSite=Lax. На вход и регистрацию действует общий лимит 30 запросов с одного IP за 15 минут.

Оформление блокирует изменения корзины этого пользователя до конца транзакции. Цены и названия сохраняются в позициях заказа. При изменении состава или цены API отвечает `409`, при недоступной позиции — `422`. Любая ошибка записи откатывает заказ и очистку корзины. Старые заказы не меняются при редактировании каталога.

## Проверено на первом этапе

Пять автоматических проверок, включая интеграцию с отдельным MySQL, прошли. В браузере проверены конструктор, расчёт, пустое название, сохранение и восстановление названия, поиск без результатов, широкий и узкий экран. Применение миграции к основной пользовательской базе зависит от доступности её учётных данных.

## Проверено на этапе покупателя

Десять автоматических проверок прошли на отдельном MySQL 8.0.46, включая CSRF, хеширование, разграничение доступа, изменение цен, одновременное подтверждение одного заказа, сохранение снимка цены, откат при искусственном сбое записи и выход из сессии.

В браузере пройден сценарий «гость → конструктор → регистрация → восстановление композиции → корзина → изменение количества → заказ → история → отмена → выход → повторный вход». Проверены неверный пароль, пустая корзина и мобильный экран. Рабочая пользовательская база не изменена: её подключение пока возвращает ошибку авторизации. Повтор заказа ещё не реализован.

## Панель администратора

После миграции `003_catalog_visibility.sql` зарегистрировать аккаунт обычным способом и локально выполнить `npm run admin:grant -- <email-аккаунта>`. Команда использует подключение из `.env` и назначает роль только существующему пользователю. Обновить личный кабинет: появится ссылка на `/admin.html`. Публичного API назначения роли нет; права проверяются по базе при каждом запросе.

Панель управляет атмосферами, нотами, флаконами, совместимостью и статусами заказов. Изображения выбираются из существующих файлов каталога `images`; загрузка файлов пока не предусмотрена. Скрытые компоненты исключаются из публичного каталога и расчёта, а содержащая их корзина не оформляется. Удаление позиции, связанной с корзиной или заказом, запрещено: её можно скрыть. Состав и цена старых заказов сохраняются.

API требует административную роль; изменяющие запросы также требуют `X-CSRF-Token`:

- `GET /api/admin/images` — список доступных изображений.
- `GET /api/admin/catalog/:kind`, `POST /api/admin/catalog/:kind`, `PUT /api/admin/catalog/:kind/:id`, `DELETE /api/admin/catalog/:kind/:id` — справочники `atmospheres`, `accents`, `bottles`.
- `PATCH /api/admin/catalog/:kind/:id/visibility` — доступность через булево поле `active`.
- `GET /api/admin/atmospheres/:id/accents`, `PUT /api/admin/atmospheres/:id/accents` — совместимость; запись принимает массив `accentIds` и выполняется транзакционно.
- `GET /api/admin/orders`, `GET /api/admin/orders/:id` — список и состав заказов.
- `PATCH /api/admin/orders/:id/status` — новый `status` и ожидаемый `expectedStatus`; при устаревшем состоянии возвращается `409`.

Списки содержат по 25 записей, параметр страницы — `page`. Каталог поддерживает `q`, `state` (`all`, `active`, `hidden`), `sort` (`name`, `price`), `direction` (`asc`, `desc`). Заказы фильтруются по `number`, `status`, `from`, `to`; даты имеют формат `YYYY-MM-DD`, последняя дата включается целиком. Допустимые переходы: `new → processing/cancelled`, `processing → completed/cancelled`; конечные статусы не изменяются.

## Проверено на этапе администратора

Все 15 автоматических проверок прошли на отдельном MySQL, включая миграции, права и CSRF, изменение каталога, атомарную совместимость, недоступные компоненты, допустимые переходы статусов, конфликт обновления и сохранность снимка заказа. Назначение роли проверено локальной командой на синтетическом аккаунте тестовой базы.

В браузере проверены гостевой доступ, добавление и изменение флакона, ошибка цены, скрытие, фильтры, пустая выдача и карточка отменённого заказа. Проверены обычный и узкий экран 390 × 844. Переходы статусов и изменение совместимости проверены автоматически через API; полный сценарий этих форм в браузере пока не пройден. Основная пользовательская база не изменялась из-за ошибки её авторизации.
